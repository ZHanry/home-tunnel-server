# Remote desktop deployment and recovery (8.0 development)

RD is disabled by default. Its control-plane tests do not establish real browser/native media interoperability or public-network performance. No 8.0 release is implied by these files.

The root Compose and example environment continue to select the published 7.0.0 images until a candidate release passes acceptance. For an isolated 8.0 source build, use a fresh project/data volume and build **both** services from this checkout: `docker build -t home-tunnel-control-center:8.0.0-rc.1 ./control-center` and `docker build -t home-tunnel-traffic-gateway:8.0.0-rc.1 ./traffic-gateway`. In that test project's environment set `HOME_TUNNEL_VERSION=8.0.0-rc.1`, `HOME_TUNNEL_CONTROL_IMAGE=home-tunnel-control-center`, and `HOME_TUNNEL_GATEWAY_IMAGE=home-tunnel-traffic-gateway`, then run Compose with `--pull never` and the RD overlay. Check both `/healthz` versions before enabling RD. Do not combine a source-built control center with an older gateway image or point the development build at a production database.

Use `deploy/compose.rd.yaml` only after generating a dedicated P-256 PKCS8 key at `deploy/secrets/rd_signing_key`, with the secrets directory accessible only to the deployment owner. The key must be readable by the container service user but must never be pasted into environment values, logs or source control. Keep the previous deployment backup before any migration.

```sh
umask 077
mkdir -p deploy/secrets
test ! -e deploy/secrets/rd_signing_key
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out deploy/secrets/rd_signing_key
```

The above assumes your container secret deployment grants the service user read access. A read-only bind mounted 0600 root-owned file is not readable by an unprivileged application UID; configure ownership for your deployment rather than making the secrets directory public.

Set `HOME_TUNNEL_RD_ENABLED=true` explicitly and `HOME_TUNNEL_RD_STUN_URLS=stun:stun.example.com:3478` only for your own available service. Empty STUN configuration permits LAN/direct candidates only. TURN, ICE-TCP and media relay are forbidden in configuration. Enabling RD on the server never enables capture or input on a desktop.

For optional address discovery, use the `stun` Compose profile with `deploy/compose.stun.yaml`. It publishes only UDP 3478. On the Linux host first validate and install `deploy/stun/firewall.nft` using `deploy/scripts/stun-firewall.sh check` and `apply`. The script never flushes existing firewall rules. Persist this table with your distribution's nftables service. Do not publish the profile until the rules have passed a syntax check on that host. Docker firewall integration and IPv6 must be verified for the actual distribution. A UDP-capable DNS record must resolve directly to the host, without an HTTP CDN proxy.

The rules bound ingress to 200 packets/s with burst 400, source meters to 10/s with burst 20 and 2048 entries each for IPv4/IPv6 (4096 total), request datagrams to 512 STUN bytes, and egress to 64 KiB/s. Counters are visible with `stun-firewall.sh status`. Ingress attacks can still count toward the cloud provider's bill. These are configured limits, not a public-load result. The versioned coturn image and `turnutils_stunclient` healthcheck still require validation on the target host; registry access and Docker were not available in the development acceptance environment.

Run `python3 deploy/scripts/probe-stun.py YOUR_STUN_HOST` from a separate permitted network. It verifies a standard Binding response and rejects a successful TURN Allocate. Before enabling users, additionally verify Refresh, Send and ChannelData rejection, firewall counters under a bounded authorized load, and that server bandwidth does not follow 10/40 Mbps media bitrate. The probe does not claim those independent checks passed.

Full encrypted backups include the RD tables, instance/restore epoch, and the dedicated key when RD identities exist. Keys and the encrypted repository password must remain under separate protection. The backup producer derives its version and supported schema from its package and migration directory, and retains support for schema 12 backups. New deployment archives ship their migration directory for recovery validation.

`deploy/scripts/import-restore.py` imports only to a new Compose project and empty volume. It verifies checksums and SQLite integrity before making a separate recovery copy, advances the RD restore epoch, invalidates RD tokens/challenges/live sessions, clears slots and disables RD globally and in the restored environment. The original backup remains unchanged. RD local grants remain host-authoritative: an old server copy must never revive a locally revoked grant. An unreachable host can continue only until its already signed lease expires; recovery cannot instantly stop an offline endpoint.

After a recovery, verify normal account/tunnel operations, compare the server key pin and endpoint identities locally, then explicitly enable RD and re-authorize hosts. Shut down RD first if a signing key is suspected compromised.

The daily per-account signaling counters record UTF-8 JSON body bytes received and serialized bytes sent on authenticated HTTP/WSS control-plane messages. They exclude HTTP/TLS/WebSocket framing and peer-to-peer media/files. Business traffic has a 20 MiB daily limit; typed authentication, heartbeat, presence, session renewal and safe closure use a separate 8 MiB reserve. New sessions also check the same persistent budget inside their database transaction. Exhaustion does not prevent a user from closing a session. Counters are persisted for each message, so process restart does not reset them. Anonymous failed requests remain covered by IP and challenge limits.

Signing keys expire after one year. Rotate before expiry using the offline utility `node deploy/scripts/rotate-rd-key.mjs OLD_KEY CURRENT_PUBLIC_KEYSET NEW_KEY NEW_PUBLIC_KEYSET`. The current public keyset is the JSON from `/api/v1/rd/server-keys`; never send a private key to that endpoint. The utility creates exclusive new files, signs the next public keyset with the previously trusted active key, preserves up to 32 historical rotation proofs, and retains the previous key for one hour so existing short leases can finish. It never edits deployed files. After verifying a fresh encrypted backup, stop the control center, install the new private key at the existing secret path and the manifest at `deploy/rd-keyset.json`, then restart with `deploy/compose.rd-keyset.yaml` in addition to the RD overlay. The server verifies the complete transition from the keyset pinned in SQLite, rejects foreign instances, rollback and unsigned replacement, and verifies its active private key matches. Clients advance trust through this same signed chain; restore epochs only revoke old sessions and never reset key trust. Keep the manifest overlay for future restarts and backups. Initial trust still needs a locally verified pin. Key compromise requires explicit re-enrollment under a new trusted deployment; a signature by a compromised key is not recovery proof.

Prefer disabling RD as rollback. Never point old server binaries at an unknown newer schema. A database rollback requires a maintenance window and an independently verified backup/restore procedure.
